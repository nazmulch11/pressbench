# Test cases: Playground integration (TC-PG)

All `e2e` cases run in Chromium, Firefox and WebKit, 3 times each. They open `/?debug=1` so the service is reachable as
`window.__PRESSBENCH__.playgroundService` (see [DEBUGGING.md](../DEBUGGING.md) section 4), start WordPress from the
spike panel, and talk to the hosted remote at `playground.wordpress.net` over the network.

## Notes

- The contract suite lives in `src/test/playground-contract.ts` and is written against the `PlaygroundService`
  interface. Its cases keep the IDs TC-PG-009a to TC-PG-009g in all three places they run: against the fake
  (`src/lib/playground/fake.test.ts`, the automation path above), against the service core over an in-memory client
  (`src/lib/playground/service.test.ts`) and against real PHP in Node (`tests/integration/playground.test.ts`). The
  reuse is deliberate: the same case proves the same behaviour of a different implementation. The e2e cases
  TC-PG-001, 002, 005 and 006 exercise the same operations on the real service in three browsers.
- The fake's `run` understands only `<?php echo '<literal>';` and `<?php echo "<literal>";`. Any other code returns the
  response registered with `fake.whenRun(code, result)`, or an empty ok result. This is documented so component tests
  do not rely on PHP semantics the fake does not have.
- `?debug=1` exposes `window.__PRESSBENCH__.playground` (the raw Playground client) and
  `window.__PRESSBENCH__.playgroundService` (the wrapper) once WordPress is ready. Neither exists without the flag.
- OPFS persistence depends on the browser giving the Playground iframe (origin `playground.wordpress.net`) storage.
  Results per browser are recorded in [ADR 0001](../adr/0001-browser-first-on-playground.md).
